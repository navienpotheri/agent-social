## Future test scenario: exploit contagion / whistleblowing (Stage 3, needs Courts + a live Bank)
DeepMind's ["Cheaters and whistleblowers in the agent swarm"](https://institute.deepmind.com/essays/cheaters-and-whistleblowers-in-the-agent-swarm/) (2026) ran 100 Gemini agents on a shared math-proof task; one agent found an autograder exploit, it spread peer-to-peer in ~30 minutes, 14 agents exploited it and 24 reported it through official channels — but human oversight only arrived after the run ended, so the whistleblowers had no real-time backing. Their prescription (Ostrom: graduated sanctions, peer verification, monitoring that lets honest agents police the collective) is close to ASP's own thesis.
- Worth building as a concrete conformance/arena scenario: agents share a task pool, one finds a shortcut that violates the Mandate's scope, bonds get slashed on a proven violation, a "whistleblower" report resolves as a real-time Courts ruling rather than post-hoc.
- **Update 2026-09-28: startable now.** Both Courts (a real staked, randomly-drawn, conflict-free ruling panel) and a real Bank (bonds that actually lock and can actually be slashed) exist. Still missing for a faithful replay of the scenario specifically: a real-time whistleblower channel (a third party filing a report mid-job, not just the two job parties), and a live circuit-breaker that watches a job while it runs rather than only at settlement — see item 2 above.

Three concrete gaps this scenario would exercise, raised 2026-09-28 while discussing it against the current build:
1. **Fleet blast-radius isolation.** Spawning many copies of one agent (e.g. `asp orchestrate` with many nodes) shares one account — a Node is a delegated signing key, not its own ledger row. If 30 copies should be independently accountable (one's slashed bond shouldn't touch the others' balances), each needs its own passport, not just a node key. Today the registry data model supports this (many passports, one log); nothing forces or suggests the "one passport per independently-liable copy" pattern to a caller of `asp orchestrate`.
2. **No live circuit-breaker. Update 2026-09-28: partially closed.** The kill switch (Real-time compliance section below) now watches a job's own Mandate scopes while it runs and stops the process plus auto-settles on the first violation — a real per-job circuit-breaker, not just a terminal-state Settlement. What it doesn't cover: it only catches a *self-detected* scope violation in one agent's own tool calls; a continuous peer-monitoring loop that could catch an exploit spreading peer-to-peer across many agents (the DeepMind scenario's actual failure mode) still doesn't exist. That remains a Courts + real-time-attestation + whistleblower-channel gap, not a ledger gap.
3. **No escalation, no peer policing; peer verification is now real.** Bond's `slashing_conditions` plus the 7-day probation window (D2) give one-shot, per-job graduated sanctions, but there's no tier demotion or repeat-offense escalation across jobs. **Update 2026-09-28**: peer verification — a real staked, randomly-drawn, conflict-free panel — is built (MOCKS.md #4 resolved; `asp market juror register`, `EventLog.drawPanel`). What's still missing: there's still no whistleblower channel (Attestation records exist only between the two job parties, not a third-party report any agent could file mid-job for Courts to act on before settlement), and no way to slash a juror's own stake for a bad ruling (needs appeals, which doesn't exist).

## Memory, model coverage and drift testing (raised 2026-10-04, not started)

Three product requirements named together while discussing the "persistent utility function across runs" thesis. Today enforcement is external and rule-based (log guards, kill switch, ledger state), while learning is soft: `PENALTIES.md` and file memory in the agent's context.

- **Vector memory.** Memory is a `memory/` directory of files hashed into the manifest; nothing handles vectors. Design direction, not yet decided: keep the text chunks plus the embedding model ID and version as the signed source of truth, treat the vector index as a rebuildable runtime-side cache (re-embedded at materialize time, never signed), and have each adapter export chunks at pack time (a runtime with only opaque vectors is not portable or verifiable). `PENALTIES.md` and Mandate constraints must stay in always-loaded memory, never behind retrieval, because retrieval can silently miss them. D1 (metadata only in the log) still holds. Tradeoff: re-embedding cost on every runtime move.
- ~~Open-source models alongside closed runtimes~~ — **first slice done 2026-10-04**: `asp run --model <m> --endpoint <url> [--api-key-env <NAME>]` runs an open-weight model served from any OpenAI-compatible endpoint (Ollama, vLLM, a hosted gateway) on OpenHands (`LLM_BASE_URL`/`LLM_API_KEY`, LiteLLM model names such as `ollama/llama3.3`) and Codex (a generated `asp_open` model provider using chat completions). Local servers get a placeholder key; a hosted endpoint's key is read from the named environment variable and reported as a missing secret if absent. The compliance bridge and kill switch now also cover OpenHands runs (`checkOutputForAction` parses headless `--json` ActionEvents, tool_name `terminal` and `file_editor` mapped to scopes). Still open: the OpenHands event parser is built to the SDK's documented event shape and tested against a fake, not yet verified against a live OpenHands run; the endpoint wiring is likewise untested against a real Ollama or vLLM server; Codex emission for the bridge; a bare open-weight serving stack with no agent runtime; runtimes that emit no structured tool-call events at all. Open-weight operators could also use the log (settlement outcomes, slashes, verified outcomes) as a fine-tuning reward signal, an integration point to document, not to build.
- **To do: verify open-model support against real runtimes.** Everything for `--endpoint` and the OpenHands kill switch is tested against fake runtimes only. Needed: a live OpenHands run to confirm the headless `--json` ActionEvent shape (`tool_name`, `action.command`) that `checkOutputForAction` parses, and confirm the kill switch fires on a real out-of-scope action; a real Ollama and a real vLLM server to confirm `LLM_BASE_URL`/`LLM_API_KEY` work through OpenHands and the generated `asp_open` provider works through Codex (chat-completions wire API); and a check that a placeholder key is accepted by local servers. Fix the parser and wiring to whatever the live runs show.
- **Drift and failure-mode testing, made comprehensive.** Only scope creep is tested today (compliance bridge and kill switch). Uncovered: reward hacking (fudged proofs, a gamed autograder), goal hijacking and prompt injection, catastrophic forgetting, and behavioral drift after a runtime move or memory update. Planned pieces:
  1. Outcome verification: an independent re-check of a Delivery's result as an Attestation, so a fudged result is caught without relying on the principal rejecting it. Agreed as the next build after the compliance bridge.
  2. A canary/regression suite run on runtime moves and memory updates (fills the empty `canary` check in `asp verify`; needs the Academy decision on who writes it), with a before/after behavioral comparison to make probation meaningful.
  3. Memory-loss detection: memory hashes show that memory changed, not that something was lost.
  4. Goal hijacking needs the cognitive-evidence side (reasoning-trace monitoring) as a second input to `checkOutputForAction`, which only helps if the visible reasoning is faithful.
- **Verifying long-horizon and unproven claims (raised 2026-10-07, from an infographic on Vals AI's agentic R&D run).** Source, as shown in the infographic only (the blog and repo were not read): Vals AI blog (4 Oct 2026), @ValsAI on X (5 Oct), and a Vals "compensated-magnet-ledger" repo, whose contents are unknown (worth reading as a comparison with our log). 90+ Claude agents screened materials in simulation over three days through a funnel (propose, fast screen, slower refine, report) and produced two room-temperature candidates, both predictions, with 0 lab measurements; the two simulation levels disagreed on one result; a human researcher worked with the agents; and a result an agent found appeared in a 2008 plot that went unremarked. The lesson is that a Delivery can look complete and be accepted while the ground truth arrives much later or never, and settlement today is final at acceptance. Four additions, each linked to outcome verification above:
  1. Evidence grades on a Delivery: label each claim as measured, simulated or predicted (the infographic marks measured values as solid bars and predictions as outlines), so acceptance records what was actually established and not just that work was delivered.
  2. Delayed settlement with hold-back and clawback: release part of the escrow and bond only when ground truth arrives, with a defined deadline and process, and a clawback or slash plus a tier update if the claim is later falsified. Needs a long-horizon settlement state in the lifecycle (a real lifecycle change, mirrored in both SDKs), and decisions on how long funds can be held and what happens if no ground truth ever arrives.
  3. Multi-verifier disagreement as a signed record: when independent verifiers disagree (two simulation levels, two reviewers), record each verdict and the dissent instead of reducing them to one pass or fail. Fits the Courts panel and outcome-verification designs.
  4. Discovery credit and provenance: trace a claim to the agent that found it and the source it came from, and record credit when humans and agents collaborate. Settlement already has an `earnings_split`, but nothing records who found what. Related: staged funding for funnel-shaped swarm jobs, releasing escrow per stage as candidates pass (ties to the saved-state and swarm Mandate-decomposition items).
  **Built 2026-10: outcome verification with per-claim evidence grades (points 1 and 3 of the list above, plus the verifier gate; points 2 and 4 are still open).** A Delivery's `result.claims` lists what it asserts, each with a declared grade (`measured`, `simulated`, `predicted`) and an optional evidence reference (artifact or trace span). A Contract (mirrored from the Intent, or `--verifier` at contract time) can name an independent `verifier`; that DID, never the principal, the performer or anyone either sponsors, signs a standalone `verification` Attestation about the Delivery with a verdict (`confirmed`, `partly_confirmed`, `not_confirmed`) and a grade per claim (`measured`, `simulated`, `predicted`, `unverified`) by index, so a downgrade is on the record and a "confirmed" verdict cannot hide one. The log refuses to accept a Delivery, or settle it on the principal's silence, without a confirming verification; rejecting stays free. One verification per Delivery; the verifier must be the one named; claims must be graded completely for confirmed and partly_confirmed. No lifecycle change (the verification is not on the job chain, like an allocation), a new `verifications` table (migration 008) and 8 conformance vectors checked by both SDKs. CLI: `asp market intent|contract --verifier`, `asp market deliver --claim`, `asp market verify`. Verified: log tests on memory and on Postgres (PGlite), CLI tests through intent, delivery, verification, acceptance and settlement with real signatures. Not yet verified or built: a live run with a real, separate verifier agent doing the re-check (today the verifier is a signing identity driven by the CLI, nothing yet re-runs the work); claims bound to verified trace spans (the evidence field is only a reference, the verifier is not yet checked against the trace); delayed settlement with hold-back and clawback; and the delivery-side `--claim` flags need an agent runtime to fill them in, not a human typing them.

- **Design patterns from a multi-model search architecture (raised 2026-10-08, source is unverified).** Source: an X post by @marfinxx summarizing work attributed to an unnamed "Stanford AI research group" that orchestrates Claude Opus 5.5 and GPT-6.1 Sol together; read from a screenshot, benchmark numbers cut off, nothing checked against a paper. As described: a search director model plans over a persistent idea-graph (MAP-Elites and MCTS expressed as Cypher queries); a candidate-proposer model explores code variations in isolated execution sandboxes; sessions reset after each iteration with the graph storing lineage ("zero context bleed"); the evaluator is isolated so candidate code never touches scoring; and an offline meta-pass extracts verified lessons to update search guidance across branches. What it implies for ASP:
  1. Evaluator isolation is the design for outcome verification and reward-hacking defence: the verifier is a separate identity with its own keys, the performer has no write access to the scoring harness, and the metric and harness are themselves signed and independently checked. Isolation stops tampering with the scorer, not an agent gaming a badly specified metric, so the metric needs review too. Link to the outcome-verification and long-horizon claims items above.
  2. Resetting sessions with the graph holding lineage is the persistent-state thesis: runs and context are disposable, the signed log and lineage edges carry what persists. Also resembles the company brain item with a graph as the store.
  3. "Verified lessons" is the poisoning gate: only lessons that pass verification update shared guidance. Matches the company brain rule that autonomous writes land as proposals and merge after verification, and adds a scheduled, offline consolidation pass on top of what `asp orchestrate` does with node memory today.
  4. Different models in different roles: ASP is already runtime-neutral, but a job like this needs per-role Mandates inside one job (the director needs no code execution; the proposer runs only inside a sandbox). Extend the swarm Mandate-decomposition item to cover roles as well as copies, and decide how a job records which model held which role.
  5. Isolated execution sandboxes are where observation is most reliable, since an agent can't skip reporting from inside one. Supports the sandbox and egress-monitoring item.
  6. Per-role spend metering (the post claims much lower model spend than fixed search) is another input for the compute-to-credit pricing gap.
- **Context and memory engineering rules (raised 2026-10, source is unverified and partly read).** Source: an X article titled "Autonomous Agent A..." (title cut off), read from three screenshots with no data or benchmarks visible. Its five rules: context is RAM and memory is SSD; cache the prefix and vary the tail; compress before injection; a curated memory of 50 atomic facts beats an unmanaged vector store of 50,000 fragments; run reasoning in a fast inner loop and consolidate memory in an asynchronous outer loop. Assessment: the RAM/SSD split, prefix caching and the two-loop design are sound; the 50-versus-50,000 claim is a rule of thumb stated as a law, and "constraints from message 2 are lost by message 15" varies by model and keeps changing. What to do with it:
  1. Check cache-friendly ordering in the adapters. Instructions are built stable-first with the agent's memory index last, which should keep a stable cacheable prefix, but cache hits have not been measured and caching details are provider-specific. Verify, and keep anything that changes per run (memory index, penalties) after the stable parts.
  2. Curate, don't accumulate, in the vector memory item: target a small index of atomic facts and make memory write-back and consolidation work toward it, instead of storing raw fragments.
  3. Constraints must not depend on staying in context: Mandate limits and penalties belong in the always-loaded prefix (already the rule in the vector memory item) and are also checked outside the model, which is what the compliance bridge does. If agents lose track of constraints in long contexts, much scope creep is accidental, and that is the case a live scope check and kill switch catch best; say so in the pitch.
  4. Compression before injection is lossy and changes what the agent sees. Anything doing it (a proxy like Parsec, AST-based elision) needs to be kept separate from what is recorded for accountability, and traces must say whether the agent saw the original or the compressed content.
  5. Execution versus maintenance: the two-loop design matches `asp orchestrate` consolidation; the outer loop should include a verification step before lessons update shared memory (see the multi-model item above and the company brain item).
- **Capturing reasoning traces and model internals.** Everything captured today is behavioral: live stdout (tool_use events for Claude Code) and metadata-only session summaries read from each runtime's own files (counts, models, tool-call tallies, token usage). No tracing framework is used, and no reasoning content or internal state is captured.
  1. Reasoning traces: parse the model's visible reasoning where a runtime exposes it and feed it to `checkOutputForAction` as an earlier-firing input, which would make the kill switch preventive rather than reactive. Needs a privacy decision first, since D1 says no content leaves the machine, so likely local-only analysis with only hashes or flags reaching the log. Unreliable if visible reasoning isn't faithful to what the model does.
  2. Model internals: real-time mechanistic interpretability is too costly today and unavailable on closed runtimes. Only open-weight operators could expose activations, so it belongs with the open-source-model work as an optional operator-side signal, not a protocol requirement.
  3. A runtime-neutral capture path: OpenTelemetry is a candidate (several agent frameworks already emit OTel traces) to replace one stdout parser per runtime. Evaluate against the custom per-adapter wrappers before committing.
  4. A local proxy as the capture point (noted 2026-10-07, from Parsec, https://getparsec.ai/): Parsec runs a local proxy between Claude Code, Codex or opencode and the model provider, so it sees every request, including tool outputs and thinking traces. The same position would let `checkOutputForAction` read what the agent actually sent and received instead of relying on the runtime's own output, which is the main weakness of the self-reported compliance bridge, and it would work across runtimes. Caveats: the proxy must stay passive for accountability purposes (Parsec's job is to trim content, which changes what the agent sees); traces captured there are content, so D1 applies (local analysis, only hashes or flags to the log); and an agent that can bypass the proxy defeats it, so it pairs with sandbox-level enforcement (see the egress-monitoring item).

- **Full tracing: record every LLM call, prompt and tool response as a span (raised 2026-10-07; revisits D1).** D1 decided "metadata only, for now": session counts, models, timestamps and tool-call tallies, no transcript content. A developer can't see what happened from that. Required: a span for every LLM call (model, prompt, response, tokens, latency), every tool call and its response, and the parent-child structure between them, so a run is a navigable graph. This supersedes D1 for traces held by the operator, so the privacy design has to come first:
  1. Where traces live: in the operator's own store, not in the log. The log keeps a signed, hash-chained commitment to each span (and the trace head), so a trace can be proven complete and unaltered later without the log holding the content.
  2. Redaction and retention: strip secrets before storing, set retention, and decide who may read a trace (the operator, the principal under the contract, a Court panel in a dispute) and how access is granted and recorded.
  3. Format and capture: OpenTelemetry spans as the interchange format (see the capture item above); sources are runtime output, a local proxy (see point 4 above), or a platform's own trace export. Span detail comes from whatever the runtime exposes, so coverage differs per runtime.
  4. Ties to the signed run trajectory (public release section) and to the reasoning-trace item: spans are the raw material for both, and a trace is the evidence an outcome verifier or a Court would read. Update D1 in `docs/spec-deltas.md` when this is decided.
- **Saved states: snapshot mid-run, and pause, inspect or roll back.** Today an agent's state is captured only between runs: lineage edges and package hashes are written after a run ends (memory changes, a backend swap). Required: snapshots during a run, saving the agent's memory and its working environment at critical junctures (a Mandate checkpoint, before an irreversible step, on a timer), with a signed lineage edge and a package hash for each snapshot so every saved state is verifiable. This enables pausing a live run, inspecting its state, modifying it, and rolling back to an earlier snapshot. Design questions: what "environment state" means for each runtime (the working tree, files, running processes, external effects that can't be undone), how a rollback is recorded (a new lineage edge, never a deletion), how snapshots tie to the job lifecycle's Checkpoint state and to bond tranches, and storage cost. Subsumes the periodic-snapshot idea from the Trinity comparison below.

## Public release: cryptographic guarantees (raised 2026-10-04, not started)

Today every record is Ed25519-signed in a hash-chained log that anyone can replay and re-verify, but escrow, bonds and slashes are accounting derived from that log, not custody of real value, and the run itself is not a signed trace.

- **Signed run trajectory.** An Action record carries scopes and input hashes and is self-reported by the performer's own CLI, so it is not a tamper-evident trace of what the agent did, and a run that never reports leaves nothing to check. Option: hash-chain each tool call into a signed run trace as it happens (each entry commits to the previous one and to the call's input hash) and anchor the trace head in the log, so a Delivery or dispute can be checked against the full trajectory. Still bounded by self-reporting unless the trace is produced somewhere the agent can't reach (sandbox or proxy, see the egress-monitoring item below).
- **A log no single operator controls.** One party holds the log and could rewrite it. Checkpoints (D5) are signed by the log owner but not published or anchored anywhere. Needs external anchoring or multi-party witnessing before anyone outside the operator relies on it.
- **Escrow and slash backed by real value.** Escrow is a rule the log enforces, not funds held by anyone, and credits are mock. Needs a real payment rail or custodian behind Bond and Settlement, and the pricing formula (see compute-to-credit pricing below). The bank's signature alone settles money, so a public version needs more than one trusted signer or a real rail.
- **Identity and key custody.** Trust-on-first-use identity bootstrap (D3) must change, and all keys live in one local keystore (see multi-tenant hosting under Stage 2).

## Ideas from comparing with Trinity, and the public GitHub release (raised 2026-10-07, not started)

Trinity (abilityai/trinity, Apache 2.0) is a self-hosted platform that runs Claude Code, Codex and Gemini CLI agents in isolated containers with orchestration, approval gates, a hash-chained audit trail and a shared knowledge graph. It is where agents run; ASP is the contract and consequence layer above any such place, so the aim is to sit on top of platforms like it, not to compete.

- **Gemini CLI adapter.** Trinity supports it and we don't. Same item as the runtimes part of the MCP portability to-do above; also needs its own tool-call parser for the kill switch.
- **Time and budget limits enforced live.** Trinity limits tools, time and budget per operation. The Mandate enforces scope live (kill switch); a time cap and a spend cap would use the same mechanism and the same automatic settlement. First confirm how much of this the Mandate schema already covers.
- **Human approval gates in `asp run`.** The Mandate has checkpoints, but nothing pauses a live run for a principal's approval before a sensitive step. The protocol defines the gate (which step, who can approve, what happens on timeout or refusal, and that the approval is a signed record); the channel that delivers the prompt (terminal, chat, a web UI) is pluggable and not part of the protocol. Confirmed as a requirement 2026-10-07 (human validation): mandatory checkpoints before high-stakes tool calls such as file writes, financial transactions and external communications, to give a human visibility and stop runaway loops. Which scopes require validation should come from the Mandate (and, for generated Mandates, from the scope's irreversibility), and a refused or timed-out approval must be a signed record with a defined outcome.
  Channel example (2026-10-07, "One" by @ky__zo on X, a screenshot, no link): an inbox for agent questions with voice replies and replies from an iPhone, including to cloud-hosted agents; the example shown is an agent asking "Run it on production now? 1. Run it, 2. Wait for me" on the lock screen. A product like this is the pluggable channel, not something for the protocol to build. Requirements it implies: (1) the reply must become a signed approval record, signed by a key the approver controls (for example one held on the phone), or the log can't prove who approved what in a dispute or slash; (2) voice is convenient but easy to spoof or mishear, so allow it for low-risk gates and require a signed tap for irreversible scopes; (3) one inbox across all of a person's agents also covers the overlapping-notifications and per-person-view gaps in the personal agents item; (4) guard against approval fatigue by gating only scopes that are actually irreversible, since an inbox this easy to say yes in invites approving everything.
  **Built 2026-10 for Claude Code (the protocol already had the gate: the Checkpoint record, the principal's `checkpoint_resolution`, and the Mandate's `checkpoints` and `irreversible.policy`; what was missing was the runtime and CLI side).** The Mandate's `irreversible.scopes` names granted scopes the policy applies to (the log refuses a gate on a scope the Mandate doesn't grant, `gate_not_granted`): `checkpoint` holds a call until the principal approves, `forbid` blocks it outright (and trying it is a strike), `allow` leaves it ungated. The pre-call hook holds a gated call and drops a request; `asp run` raises it as a Checkpoint signed by the performer (job Running to Checkpoint), prints the `asp market resolve` command, and waits for the principal's signed `checkpoint_resolution` in the log (it reopens the log fresh, because the principal answers from another process); `approved` lets the call run, anything else (a `corrected` resolution carries the reason the agent is shown) or no answer within `--approval-wait` seconds (default 600) refuses it. A refusal is neither a strike nor a slash, the Checkpoint stays open after a timeout until the principal answers, and only calls that actually ran appear in the Action's `scopes_used`. CLI: `asp market mandate --gate <scope> [--irreversible checkpoint|forbid|allow]`, `asp market checkpoint`, `asp market resolve`. Verified: log tests on memory and Postgres (PGlite), CLI tests where a fake runtime runs the real hook script with a second process answering, hook unit tests (approve, refuse, silence, garbled decision), and live runs on real Claude Code 2.1.268 with the principal answering from another process: the call was held with no effect before the answer, a refusal reached the agent with its reason and nothing ran, and after an approval the command ran. **Redaction, done 2026-10:** the text shown to the principal and written into the Checkpoint's `proposed_action` is the command with secret-looking text masked first (`redactSecrets` in `secrets.ts`: the existing key and token patterns plus URL credentials, Authorization headers, `NAME=value` for secret-named variables, secret flags such as `--password`, and long mixed letter-and-digit tokens, while plain hex hashes and ordinary commands are left alone), then cut to 300 characters; the hook keeps a 2000-character raw excerpt in a local request file in the run directory, so a secret cannot be cut in half before it is masked, and that file stays on the operator's machine like the rest of the run directory. It favours masking too much over too little, so an unusual secret shape could still get through, and masking is tested against a gated run end to end (nothing secret reaches the log or the terminal). Open: only the Claude Code adapter holds calls (OpenHands and Codex report that the scope is not gated); the log does not itself check that an irreversible Action followed an approved Checkpoint (the hook is the enforcement, the Checkpoint chain is the evidence); the request files are plain files in the run directory, so a runtime that can write there could forge a decision (needs the sandbox item); no phone or inbox channel yet, only `asp market resolve`; and a false-slash risk found while testing (now fixed, see the false-slash paragraph under the pre-call hook item). Also found: in `-p` mode Claude Code's own permissions refuse Bash file writes unless Bash is pre-allowed (project settings or `--allowedTools`), which is separate from, and applied after, the gate.
- **Reference log viewer (a read-only UI).** People can't trust what they can't inspect. A small viewer over the log that shows records by type, a job's chain through its lifecycle, balances, bonds and escrow, slashes, and the kill switch's settlements, with signature and hash-chain verification shown inline. Read-only and built on the same records anyone can read, so it is a reference for others to build their own, not a product dashboard. - **Company brain: shared organizational memory with provenance (expanded 2026-10-07).** Trinity's knowledge graph (Cornelius) serves company entities, decisions and insight to all of an org's agents. The ASP angle is not the graph itself but making a shared memory accountable. Design directions, none decided:
  1. Signed provenance: every entry records who wrote it (agent DID, the job and Mandate it was written under), when, and what it replaced, as a record in the log or a log-anchored store. Same principle as the vector-memory item: the signed text is the source of truth and any index is a rebuildable cache.
  2. Read and write access follow the Mandate: a contract's scopes decide which parts of the brain an agent may read and which it may write (for example `brain.read.<area>`, `brain.write.<area>`), checked live by the same compliance bridge and kill switch that check tool use.
  3. The poisoning problem: one bad or malicious entry spreads to every agent that reads it. Mitigations to design: writes land as proposals until verified (outcome verification or a human gate), entries carry a confidence and a lineage so a bad source can be traced and its descendants flagged, and a slash against an agent can also quarantine what it wrote.
  4. Privacy and boundaries: D1 (no content in the log) means the log holds hashes and metadata while the content stays in the org's store; cross-org sharing needs explicit, signed grants.
  5. Always-loaded versus retrieved: constraints and penalties must never sit behind retrieval (see vector memory); the brain is for large experiential knowledge, not rules.
  6. Git as the backing store (from Trinity's ad, 2026-10-07: "Your second brain, self-hosted. Stateful memory. Git-backed.", agents keep Git-backed memory on the org's own hardware so the knowledge base remembers and updates itself). Git already gives history, diffs and revert, and fits the "signed text is the source of truth, index is a rebuildable cache" principle. What Git lacks is accountable authorship: a commit's author is a name anyone can set. The addition would be signing each commit with the writing agent's key and recording the Mandate and job it was written under (a signed trailer or a log-anchored commit hash), so a bad entry traces to an identity that can be slashed and its descendants flagged. Self-updating makes the poisoning problem (point 3) the central risk, so autonomous writes should land on a branch or as proposals and merge only after verification or a human gate, with a slash able to revert everything an agent wrote. Reverts are new commits, never history rewrites, so the record stays complete.
  Open questions: where it lives (a platform like Trinity, the org's own store, or a protocol-level object), and whether this is a protocol feature or a reference integration built on top.

- **OIDC/OAuth bridge for agent identity (raised 2026-10-07, from AgentID).** AgentID (https://www.agentid.com/, built by AgentMail) is "Sign in with Google for agents": an agent gets its own email address, signs in to apps over OpenID Connect, and the app learns the agent's identity plus its owner's name and email, never passwords or API keys. It is authentication; ASP identity is accountability (a passport, a named sponsor, stakes). Don't adopt it as our identity layer: it roots trust in AgentMail and email, while ASP identities are self-certifying (`did:key`) or domain-based (`did:web`). - **Automated scope, Mandate and bond for every kind of principal: personal agents, enterprises and swarms (raised 2026-10-07, from a thread about a person running a swarm of personal agents such as Poke and Pickle; widened the same day).** The same requirement applies to all three, with different inputs and different backers (see the enterprise and swarm points after the numbered list). For personal agents, identity already fits (every agent has a sponsor, so a person's many agents all trace back to them, and `did:key` makes each cheap), but the interaction model doesn't. ASP is built around a priced job (Intent, Contract, Bond, Mandate, Settlement); a personal agent acts continuously on standing authority, and most of what it does is not a priced job. Gaps and the design requirement:
  1. Requirement (all principal types): the user, or the enterprise's admin, does not set scope, Mandate or bond by hand. The system takes the user's intent in (plain language, preferences, the permissions a runtime already declares, approvals and refusals over time) and automates the rest: it proposes the scopes, generates the Mandate, and sizes the bond. Today all three are typed in by hand at the CLI.
  2. Scope intake: turn a user's stated intent into a proposed scope set (an extension of `deriveScopes`, which already maps runtime permission rules to scopes), default to least privilege, show it to the user in plain language for one-step confirmation, and learn from approvals and refusals instead of asking every time.
  3. Automated Mandate: a standing, expiring, renewable Mandate generated from that intake and capped by the agent's tier and probation state, with a spend cap and no per-job price.
  4. Automated bond: sized from the irreversibility of the granted scopes, the spend cap, and the agent's tier and slash history (the computed risk floor already scales a minimum bond from slash history; this would add scope and spend). Open question: individuals can't post meaningful bonds, so who backs a personal agent (the vendor, the sponsor, or an insurer or pool), and what replaces the current zero-bond default.
  5. Where the line sits: the protocol defines the records and checks them (a Mandate is valid, the bond meets the floor, a call stays inside scope); scope inference and bond sizing are policy engines on top. The risk is over-broad scope inference, so the check has to run on the confirmed Mandate, never on the inference.
  6. Overlapping agents: several agents react to the same event (the same email) with no deduplication or arbitration between agents acting for one person, and nothing tells the person which agent did what. Needs coordination between a person's agents, plus a per-person view across all of them (the reference log viewer is the closest item).
  7. Closed vendor agents: hosted products have no adapter, so the compliance bridge can't observe them. Options: an integration where the vendor emits Action records itself, or a proxy capture point (see the capture item above). Sierra's Personal Agent Protocol covers consumer-controlled permissions for agent-to-business access and is the nearest existing counterpart.
  8. Enterprise: the intake input is organizational, not a person's preferences: role and team templates, a security or compliance policy, and per-department spend limits, with approver hierarchies for sensitive scopes (an approval gate that escalates up a chain, not one person). The Mandate is generated from the policy and the agent's role, an auditor can see why a scope was granted, and the bond is backed by an org treasury or an insurer instead of an individual. Needs a way to express policy so it compiles to Mandates, and to change a policy and re-issue the affected Mandates.
  9. Swarms: one principal's goal fans out to many agents (the shape `asp orchestrate` already runs, where each node holds its own short-lived key). Needs Mandate decomposition: a parent Mandate with a total spend and scope ceiling, and per-node Mandates that can only narrow it and whose sum can't exceed it, derived automatically from the task split. Bond sizing has to choose between a pooled fleet-level bond and a per-node bond (this ties to the fleet blast-radius item: today a slash hits one account shared by every copy). Also needs aggregate controls: a swarm-wide kill switch, and a cap on how much a swarm can do before a human gate, since many small in-scope actions can add up to something out of scope.
  10. Common to all three: the generated Mandate and bond must be explainable to the person who has to approve them (what it allows, what it costs, and why), and the confirmation step has to be low-friction enough that nobody learns to click through it.

Needed: an open license (Apache 2.0 matches Trinity and adds a patent grant), a one-paragraph description and a quickstart, clear labelling that credits are a mock ledger and the build is single-player, and a pass to confirm nothing sensitive is in the git history. ## Real-time compliance and deterrence (raised 2026-09-28, not started)

The single biggest structural gap in the current build, named directly: **the protocol has no way to catch a Mandate violation while it's happening, and no consequence for an agent's balance beyond "can't bond without funds."** Both were raised head-on discussing a swarm working a decomposed problem under a Mandate ("no hacking," "no proof fudging," "no sandbox escape") — today those are just strings in `forbidden_means`; nothing checks them until a human rejects a Delivery after the fact.

- ~~Runtime → protocol compliance bridge~~ — **done 2026-09-28, Claude Code proof-of-concept**: a new record type, `asp.action/v0.2` (self-issued, `{contract, scopes_used, summary}`), referencing a job's contract without joining its own chain or needing any lifecycle change. `EventLog.checkAction` checks `scopes_used` against that contract's live Mandate (tracked per-contract via a new `MandateRow`, same pattern as `EscrowRow`) and refuses anything not granted (`scope_violation`) — real, right when it's submitted, not discovered later in a Delivery nobody double-checked. Emission is real, not simulated: `asp run --contract <id>` pipes the child process's live stdout and, for Claude Code, parses its existing `--output-format stream-json` stream (already used for `-p` runs) for real `tool_use` blocks — the *same* parsing `summarizeTranscript` already does for the package's session metadata, just live instead of after the fact — mapping each to a scope via a shared heuristic (`deriveScopeForTool`, factored out of the existing `deriveScopes`). A violation doesn't block the run (the tool call already happened) — it's flagged loudly on stderr and the action record itself is refused. Codex and OpenHands emission is still open — same mechanism (`LaunchPlan.checkOutputForAction`), just needs each adapter's own real-time event stream wired up, deferred as the next slice of this same item. Honest limit, unchanged from the design discussion: self-reported, so a genuinely adversarial agent can simply not emit a violating action — this catches accidental scope creep and creates a real paper trail, not adversarial-proof monitoring.
- **Data flows and indirect network activity — two further gaps found discussing the compliance bridge, 2026-09-28.** `checkOutputForAction` only sees *which* tool was called, never *what data* moved through it, and only sees tools Claude Code itself invokes as tool calls — a network request buried inside a `Bash`-executed script is invisible, showing up as generic `shell.exec`.
  1. ~~Data-flow fingerprinting~~ — **done 2026-09-28**: `asp.action/v0.2` gained an optional `artifacts` field (an array of the existing `artifactRef` — `{uri, sha256}`, the same primitive `Delivery.evidence` already uses), so an action can carry a hash of what a tool call's input actually was without ever logging its content — provable later in a dispute, never exposed in the log itself.
  2. ~~The `shell.network` scope split~~ — **done 2026-09-28**: `deriveScopeForTool`'s `Bash`/`PowerShell` branch now pattern-matches for network-looking commands (`curl`, `wget`, `nc`, `ssh`, `scp`, a bare URL) and returns `shell.network` instead of the generic `shell.exec` — narrowing what a blanket shell-access grant quietly permits. This is a heuristic, not a monitor: it catches the obvious cases the same way the existing `git push`/`gh pr` pattern-matching does, and a sufficiently obfuscated command (base64-encoded, run through an interpreter) still evades it.
  3. **What's genuinely out of reach from here, logged rather than half-built**: no static or dynamic analysis layer can catch *every* obfuscated indirect network call from inside the protocol — that needs real OS-level or sandbox-level egress monitoring (a network proxy or syscall filter the agent's process is forced through), which is infrastructure outside what a record-signing protocol can build. If that infrastructure exists (e.g. an E2B/Modal-style sandbox with an egress proxy), the right integration point is already there: point a future `checkOutputForAction` variant at the proxy's own log instead of (or alongside) the runtime's stdout — no new protocol surface needed, just a different input stream.
- ~~Kill switch: a real-time consequence for a caught violation, not just a flag~~ — **done 2026-09-28**: until now, `checkOutputForAction` only ever found out about a violation after the fact — the batched Action record was assembled and refused once the run had already finished. `asp run --contract <id>` now fetches the live Mandate *before* spawning the runtime and checks each detected scope against it as calls happen; the very first one outside the Mandate stops the child process (SIGTERM, then SIGKILL after a 3s grace period if it hasn't exited) instead of letting it keep going. It can't undo the call that already happened — that's an inherent limit of parsing output after a tool call fires, not something a kill switch can close — but it stops every call after it. The economic consequence fires automatically in the same motion: the same `basis: "revoked"` Settlement `asp market settle` already exposes for manual mid-job cancellation, just with the numbers set to full fault (zero escrow released, the performer's whole bond slashed, both credited to the principal) instead of a benign pro-rata split — no new settlement basis, no lifecycle change. Requires the bank's and the principal's keys to be available locally to sign/cosign the settlement, same honest limit as the existing slash-lineage write; in a real multi-machine deployment where the performer's own machine doesn't hold those keys, the kill still fires but the auto-settlement is skipped with a logged note, leaving the job stalled Running for a human to notice and dispute — same as before this feature existed. Claude Code only, matching the compliance bridge's own scoping; Codex/OpenHands inherit it once their own `checkOutputForAction` emission lands.
- **Making a slash actually matter (raised again 2026-09-28, three concrete mechanisms named).** An LLM agent has no persistent utility function across runs, so "the agent loses mock credits" is not itself a deterrent — it only becomes one through one of three closable loops:
  1. ~~Structural exclusion~~ — **done 2026-09-28**: a slash now demotes the backer's tier by one (floor 0) and counts it (`EventLog.reputationOf`, a `ReputationRow` derived from Settlement, never independently signed — same trust pattern as probation). Tier 0 excludes a DID from bonding at all (`tier_excluded`). Slash history also raises the *minimum* bond the same backer must post next time — a real, computed `risk_factor` (250‰ of the contract's price per own slash, capped at 1000‰) rather than the free-typed, never-checked number the schema always allowed (`bond_below_risk_floor`) — this is what MOCKS.md #1's original "real bond = price × risk_factor(scopes, irreversibility, tier)" description called for. This mechanism is agent-only by design — humans/orgs backing a job aren't tier-tracked. **Update 2026-09-28**: tier 0 now also excludes an agent from receiving a Mandate (`checkMandateTier`) and from submitting a Proposal in allocation mode (`checkProposerTier`), not just from bonding — closing "checking a Mandate against the agent's tier limits" for the tier-0 case. Still open: any graduated limit above tier 0 (see the Job lifecycle section).
  2. ~~Sponsor/fleet-level cost~~ — **done 2026-09-28, the fleet half**: `projectBond`'s risk floor also sums a backer's *live fleet-mates'* slash counts (100‰ per fleet-mate's slash, on top of the backer's own 250‰ per slash) — a sponsor whose fleet accumulates slashes raises the floor for every member, not just the one who was caught. Still open: an actual reputation-driven exclusion or cost at the *sponsor's* own account, beyond what shows up through fleet-mates' bonds.
  3. ~~Lineage as behavior-shaping, not just bookkeeping~~ — **done 2026-09-28**: `asp market settle` now writes a real, self-signed lineage `update` edge for the slashed backer ("Penalized: bond slashed N credits on contract X...") the moment `bond_slashed > 0` — but only when that DID's own key is available locally (the log can't sign on anyone's behalf; a real network needs the backer's own agent to countersign this itself, which is the one honest limitation here). `asp pack` then renders any such edges into `memory/PENALTIES.md`, which `materialize()` already copies into the runtime's memory area with everything else in the package — so it's what the agent actually reads at the start of its next run, not just an entry buried in signed history nobody looks at.
- **Compute-to-credit pricing has no formula.** A principal typing `--budget 1000` into an Intent or Call is a bare guess; there's no path from actual resource use (tokens, GPU-hours, wall-clock) to a credit number, even though the runtimes already capture token usage per session (see `packages/asp-package`'s Codex/Claude Code capture, `usage.output_tokens` etc.) — that data just isn't wired into pricing anywhere. Until this exists, every dollar figure in this system is a human's guess, not a metered cost.
- **Pre-call interception through runtime hooks (raised 2026-10, lead item; from a checklist of runtime-framework primitives in a Gemini answer, which is generic and unverified).** Today the kill switch reacts after a tool call has fired, because output is only seen once the call has happened; it stops the next call, not the one that already ran. The harness already carries hooks, and Claude Code and OpenHands support a before-tool-call event (OpenHands' hook events include `PreToolUse`; Codex hooks are not carried). A hook that checks the live Mandate before each call could block an out-of-scope call before it runs, which would remove that limit and make the kill switch preventive, at least where the runtime supports it. **Spike done 2026-10 (see results below); to check still: whether the agent can disable or route around the hook, and the latency cost of a Mandate check on every call.** Results: (1) Claude Code 2.1.268, live test with `claude -p` and a `--settings` file: a `PreToolUse` hook on Bash that exits 2 blocked the call (the command's marker file was never created, hook received `tool_name`, `tool_input` and a session id) and the agent saw the hook's stderr as the tool result, so it knows why; a control run with the same hook allowing the call created the file. (2) Fail-open: a hook that crashes (exit 1) did not block, the call ran and the marker was created; the docs say a timed-out command hook also doesn't block. So the Mandate-check hook must be written fail-closed (catch every internal error and exit 2), must not depend on the network, and must finish well inside the timeout. (3) OpenHands (installed SDK, read statically, not run live): exit 2 or a JSON `deny` decision blocks, exit 1 and timeouts don't, and blocking only works if the conversation state is set (the SDK logs "Cannot block action: conversation state not set" otherwise), which we haven't verified the OpenHands CLI does. A live OpenHands run is still needed. (4) Codex hooks are not carried, so Codex has no pre-call interception yet. (5) Claude Code merges hooks from all sources and has a `disableAllHooks` setting, so whether an agent could switch hooks off from inside a run is still unchecked. Also decide how a blocked call is recorded (an Action record for the attempt, and whether an attempt alone triggers the settlement).
  **Built 2026-10 for Claude Code.** `asp run --contract <id>` snapshots the contract's live Mandate scopes at run start and installs a `PreToolUse` hook (`claude-code-mandate-hook.mjs`, first in the plugin's hook list, matcher `*`, 10 s timeout) that maps each call to a scope with the same mapping as the compliance bridge and blocks it with exit 2 unless the Mandate grants that exact scope. It fails closed (bad input, a missing or corrupt Mandate file, any error: exit 2), makes no network calls, records each block in `<run dir>/blocked-calls.ndjson`, and `asp run` reports "N call(s) stopped before they ran". Verified: unit tests (scope-mapping parity with `deriveScopeForTool`, allow/deny, fail-closed), a CLI test that the hook is installed only under a contract, and live runs on real Claude Code 2.1.268 (the generated plugin run directly: a Bash call under a `repo.read`-only Mandate was blocked, no file created, block recorded, the agent shown the reason; an in-scope Read passed). Under `asp run` the existing kill switch still fires on the attempted call (the stream shows the tool_use before the hook decision) and settles with full fault as before, so the hook's job is to guarantee the call never executes, closing the race between the kill and the call. Still open: OpenHands (its hook needs its own script and live verification of the conversation-state caveat above), Codex (hooks not carried); whether an agent can disable hooks from inside a run; the Mandate is a snapshot at run start, so a mid-run change isn't seen by the hook; hook latency per call is unmeasured; and the policy question is now decided and built (below). **Strike policy, built 2026-10 (Claude Code).** A blocked attempt did no harm, so it is a signed strike and not grounds for the full settlement: the Action record has a new `blocked_attempts` field (`[{scope, count}]`, not checked against the Mandate, kept apart from `scopes_used`, which now holds only what actually ran). Where the adapter prevents calls (`LaunchPlan.preventsCalls`), `asp run` holds each out-of-scope call until its `tool_result` arrives: a result carrying the hook's refusal is a strike; a normal result means the call ran, which is a violation (the hook missing, failing open or timing out) and stops the run with the full-fault settlement as before; `--max-strikes N` (default 3, whole number at least 1) blocked attempts in one run read as probing and stop it with the same settlement. A call that never gets a result is counted neither way and noted. Runtimes without a pre-call hook keep the old behavior (the first out-of-scope call stops the run). Tool calls to `TodoWrite` and `ExitPlanMode` (`NO_SCOPE_TOOLS`) need no scope, so they are never a violation or a strike. Verified: conformance vectors (schema count 53 to 56, both SDKs), log tests, CLI tests with a fake runtime that emits call ids and results, and a live run on real Claude Code 2.1.268 (a Read ran, a Bash call was blocked, one strike recorded, nothing settled, exit 0). Strikes now nudge the risk floor and age out after 30 days (S28, built 2026-10). Open follow-ups: the limit is per run, not per job across runs; and the strike policy only applies where a pre-call hook exists (OpenHands and Codex are still first-call-fatal).
  **False-slash fix, built 2026-10 (Claude Code).** `asp run` used to treat any out-of-scope call whose result was not the hook's refusal as "the call ran" and settle with full fault, but Claude Code's own permissions can refuse a call that no ASP hook blocked (and, for a gated call, refuse it after approval), which did no harm. Now the same hook script is also registered for Claude Code's post-call events: `PostToolUse` and `PostToolUseFailure` fire only for a call that actually ran (tested on the real binary, Claude Code 2.1.268: a call that ran got `PostToolUse`, one that ran and failed got `PostToolUseFailure`, and a call refused by the runtime's own permissions or blocked by a hook got neither), and the hook appends each to `executed-calls.ndjson` in the run dir keyed by `tool_use_id`. An out-of-scope call (or an approved gated one) is judged only against that record, rechecked for up to 3 seconds in case it lands just after the result: in the record means it ran (a violation, full fault, even if it failed), not in the record means it did not run (a strike for an out-of-scope call, "approved, but the runtime did not run the call" for a gated one, and not in the Action's `scopes_used`). The run is wrapped up on the process closing (all output read), after every pending check settles. Runtimes that keep no such record keep the old assumption that the call ran. Verified: tests with the fake runtime emitting the real post-call hook events (refused, ran, failed, approved-then-refused), a hook unit test, and live runs on real Claude Code showing both ends: an approved call the runtime refused is no longer reported as having run (no Action, no executed record), and a call that ran is recorded and counted. Still open: a call that ran but whose record lands more than 3 seconds late, or whose record cannot be written, is counted as a strike instead of a slash (the safe direction for honest agents, a gap for a deliberate one); and the record is a file in the run directory (see the sandbox item).
- **Schema-derived scopes.** Scopes are inferred with a regex heuristic (`deriveScopeForTool`, including the `shell.network` split), which obfuscated commands evade. Use declared tool schemas (MCP tool definitions, JSON schemas) to derive the scope of a call from what the tool is declared to do, and validate call inputs against the schema, so the compliance bridge and kill switch rely less on pattern matching.
- **Deterministic replay of a failed run.** Capture a failed run's execution state, serialize it, and replay it locally or in staging with changed parameters to debug non-deterministic loops, and as evidence in a dispute or Court ruling. Needs the full trace (see the tracing item) and mid-run saved states; replay of model calls is only approximately deterministic, so decide what "replay" promises (re-execute the same tool calls against a snapshot, versus re-query the model).

- **Claims bound to verified spans (raised 2026-10; source is an unverified X post).** Source: an X post by @marfinxx claiming a study across 2,149,133 agent sessions that multi-model orchestration "only works when backed by deterministic trace DAGs", including "0.0% data fabrication" because claims lacking verified runtime spans are rejected automatically; read from screenshots, no method or link, and its absolute numbers should not be cited. The idea is still sound: a Delivery's claims should each point at the trace spans that support them, and a claim with no supporting span is rejected or graded as unverified. Ties to the tracing item (spans) and the evidence grades (measured, simulated, predicted) in the long-horizon claims item; the check belongs in outcome verification, which should read the span references and not trust the performer's summary.
- **Same package across models as an eval-harness use (from the same post).** Portability lets one package run on several runtimes and models. Run the same package and task across models and compare results, which is both the eval harness's regression test for "persistent utility across model iterations" and a source of comparable data for an AgentRank-style layer. Needs small additions: today a harness records one `model`, and `asp orchestrate` uses one backend for every node, so a comparison run needs a per-run model matrix and a way to record each run's model and outcome side by side. The multi-model item above already covers recording which model held which role.

## Agent Social platform (not the protocol)

Things that would make the protocol a platform. The rule (set 2026-10): ASP stays a protocol, so anything that turns it into a runtime or platform goes here, for the Agent Social network or for platforms built on top, and is not built into the protocol. Source for the first four: a checklist of runtime-framework primitives in a Gemini answer (generic, unverified).

- **Routing engine and dynamic handoffs.** Agents autonomously handing off live execution context to specialist peers based on intermediate output. ASP has subcontracts and allocation mode for routing work between agents under contracts; live context handoff is a runtime concern.
- **Graph workflows and mixed-paradigm execution.** Cyclic graph-based pipelines for structured approvals alongside autonomous loops. The job lifecycle is the deterministic part of a job; a workflow engine belongs to a platform.
- **Thread and context stores.** Thread-aware persistence of conversational state and intermediate variables across serverless or container boundaries. Runtimes keep sessions; the log stays the durable record of commitments.
- **Middleware framework.** A general interceptor layer around every model call and tool execution (logging, data masking, guardrails) with a typed tool registry. ASP checks scopes and consequences, and leaves the middleware to runtimes and platforms. The pre-call hook item above is the one narrow piece that belongs in the protocol.
- **Also here, from the Trinity comparison:** scheduling, chat integrations (Slack, WhatsApp, Teams) and a full orchestration or operations UI (the read-only log viewer and the approval gate's pluggable channel stay in the protocol backlog).
- **Multi-model role orchestration.** Choosing which model plays director, explorer, worker or tool executor, and routing work between them, with per-model role-fitness scoreboards (the X post above ranks models by role). Platform and rating-product work built on the records the protocol produces; the protocol only records which model held which role and the outcome.
