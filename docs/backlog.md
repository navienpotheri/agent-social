## Job lifecycle
- ~~Principal-mode silence counting as acceptance~~ — **done 2026-09-28**: a real lifecycle change (not just wiring), scoped separately from the batch it was raised in. `Contract` gets an optional `review_deadline` (mirrored from the Intent's `verification.review_deadline` by `asp market contract`); `Settlement.basis` gets a fourth value, `"silence"`; a new lifecycle transition (`Delivered → Settled`, issued by the bank, guard `past_review_deadline`) lets the bank settle without ever citing an acceptance, once the settlement's own timestamp is past that deadline. Mirrored in both SDKs (`packages/asp-core/src/lifecycle.ts`, `python/src/asp_core/lifecycle.py`) with two new shared conformance vectors (`silence_after_deadline`, `settle_before_deadline`) — this is a lifecycle-level change, so conformance vectors are the right place, unlike the asp-log-only extensions above. `asp market intent --review-deadline <iso>` and `asp market settle --basis silence` expose it (docs/spec-deltas.md S17).
- Panel fees and appeals on a ruling
- ~~Subcontract nesting~~ — **decided and done 2026-09-28**: an agent can hold the principal role on a subcontract, funded from its own balance — no automatic netting back to the parent's escrow; `parent_contract` links child to parent for audit only. `EventLog.checkSubcontract` makes this a real, checked relationship rather than an unvalidated field: the parent must exist and actually be a Contract, must not already be Settled, and the child's `principal` must be the parent's own `performer` (a subcontract is that performer hiring help for work it's already on the hook for, not an arbitrary DID borrowing someone else's job id). `asp market contract --parent-contract <id>` (docs/spec-deltas.md S18). Still open, deliberately deferred as a separate question: whether the parent's Mandate (forbidden_means, scopes) should propagate to children automatically, or each child gets its own from scratch — today it's the latter (nothing propagates).
- ~~Checking a Mandate against the agent's tier limits~~ — **done 2026-09-28, the tier-0 half**: `EventLog.checkMandateTier` refuses a Mandate whose performer has been demoted to tier 0 by repeat slashes (`tier_excluded`), and `checkProposerTier` does the same for a Proposal in allocation mode. Still open: any *graduated* limit above tier 0 (e.g. tier 2 capped at a lower `spend.cap` or fewer `scopes`) — there's no spec-defined mapping from tier to specific Mandate limits yet, only the binary "0 is excluded, 1+ is not."
- ~~Settlement amounts aren't derived from a ruling's `fault` percentages~~ — **done 2026-09-28**: `projectSettlement` now derives `escrow_released`/`bond_slashed` from the cited ruling's fault on the performer (`floor(escrowLocked × (1000 − fault) / 1000)` / `ceil(bondLocked × fault / 1000)`) and rejects a mismatch outright (`settlement_mismatches_ruling`) — a bank can no longer rule one way and settle another. `asp market settle` derives the same numbers automatically when `--escrow-released`/`--bond-slashed` are omitted, so callers don't hand-compute the formula (docs/spec-deltas.md S13).
- ~~`asp market` covers assignment mode only~~ — done 2026-09-28: `asp market call`/`propose`/`allocate` add allocation mode (Call→several Proposals→a panel member picks one), and `asp market contract` accepts either `--intent`/`--offer` or `--call`/`--proposal`. Call/Proposal aren't chained (same as Intent/Offer), so this needed no lifecycle change.
- ~~`asp market` doesn't drive the dispute path~~ — done 2026-09-28: `asp market deliver` already redelivers (the lifecycle's own `redelivery_available` guard applies), and `asp market rule` adds the ruling step (Courts, narrowly — see MOCKS.md #4 for what's still mocked about it) so `asp market settle --basis ruling` works too.

## Registry
- ~~Revoking a node before it expires, and revoking a person's nodes when its keys rotate~~ — done: a second Node record chained onto the first (`prev` = its id) is an update; setting `expires` at or before `issued_at` revokes it immediately (`revokedAt` is set, so the key becomes entirely unresolvable, not merely expired). Dropping a passport key now also revokes every one of that person's live node keys, since the delegations were made under a key that's being retired.
- Requiring node keys whenever the actor is a node (a person's own key can still sign for its node) — left as is; tightening this could break legitimate recovery (a person acting as its own node when a delegated key is lost), so it needs a decision, not just a change.

## OpenHands (reported at run time)
- Its sessions aren't indexed into the package's experience: OpenHands' own conversation store (`~/.openhands/conversations/<id>/base_state.json` and its `ConversationMetadata`) records no working directory or project association at all, unlike Claude Code (nests conversations under a directory named for the project) and Codex (`session_meta.cwd` in every rollout). There's no reliable way to tell which of a user's past OpenHands sessions belong to a given project, so indexing them would mean guessing (wrong) or scanning event content for file paths (fragile and expensive). Sessions `asp run`/`orchestrate` start themselves are already isolated per run (`OPENHANDS_CONVERSATIONS_DIR` points at the run folder), so this only affects capturing a project's pre-existing history.
- Path-scoped rules are on-demand skills naming their globs; OpenHands has no path triggers
- Permission rules are stated, not enforced; headless OpenHands auto-approves every action, with the WSL user's full permissions
- Hook events OpenHands lacks are dropped


## Bank (credit ledger)
- ~~`fees`... aren't credited to anyone~~ — **decided and done 2026-09-28**: `fees` now comes out of the same escrow, on top of `escrow_released` (checked against what was actually locked, same as any other over-release), and credits to `EventLog.PLATFORM_DID` — a local mock account, same trust boundary as the mocked bank/panel DIDs in `conformance/generate.ts` (MOCKS.md), standing in for a real platform/Insurer recipient. `asp market settle --fees <n>` (docs/spec-deltas.md S18). `earnings_split` (a different field, splitting the performer's own share with e.g. a fleet/sponsor) is still untouched — nobody's asked for it yet and it's a separate design question from where fees go.

- ~~Bond's `slashing_conditions`... nothing yet *decides* when a slash is warranted~~ — done 2026-09-28: a real, staked, randomly-drawn, conflict-free ruling panel now decides (`asp market juror register`, `EventLog.drawPanel`/`checkRulingPanel`; docs/spec-deltas.md S12). What's still missing: nothing ever slashes a *juror's* stake for a bad ruling — that needs an appeals process, which doesn't exist (see below).
- No appeals on a ruling, and so no way to slash a juror's own stake for misconduct (self-dealing, a ruling later overturned) — the stake exists and is real credit at risk, but nothing can currently act on it. **Decision 2026-09-28: deferred deliberately, scoped as its own future slice** (not a "no," just "not now") — this is the biggest of the four decisions raised that day, needing a real second-panel/overturn design (who can appeal, drawn how, within what window, what fraction of the original panel's stake is at risk) before any code, the same way silence-as-acceptance turned out to need its own pass.

## Stage 2 / hosted network
- Multi-tenant hosting: today `~/.asp` is single-user, single-machine — one local keystore, one local event log, no auth layer. A hosted network needs per-tenant auth boundaries, data isolation between orgs, rate limits and billing separation. The registry's data model (many persons/orgs/fleets in one log, sponsor-based isolation rules) already supports this; the deployment and auth layer around it does not exist yet.

## Orchestrator (`asp orchestrate`)
- Consolidation is a plain merge (line-union for MEMORY.md, side-by-side keep for conflicting files) — no LLM judge resolves contradictions or dedupes near-duplicate lessons the way the spec's "consolidation step" ultimately should
- No Mandate/Contract wraps a fleet run yet (see MOCKS.md #12), so `nodes.max_parallel` isn't enforced by the registry, only by the CLI's own `--max-parallel`
- ~~Node grants aren't revoked early if a node's task is abandoned~~ — **done 2026-09-28**: the moment `asp orchestrate` detects a node's task failed (a nonzero exit, a hidden failure, or the runtime not starting at all), it chains an immediate revocation onto that node's own grant (same pattern as manual node revocation) rather than leaving the key live until its natural expiry.
- No retry or backoff for a failed node; a failed task is just reported and excluded from consolidation

## Future test scenario: exploit contagion / whistleblowing (Stage 3, needs Courts + a live Bank)
DeepMind's ["Cheaters and whistleblowers in the agent swarm"](https://institute.deepmind.com/essays/cheaters-and-whistleblowers-in-the-agent-swarm/) (2026) ran 100 Gemini agents on a shared math-proof task; one agent found an autograder exploit, it spread peer-to-peer in ~30 minutes, 14 agents exploited it and 24 reported it through official channels — but human oversight only arrived after the run ended, so the whistleblowers had no real-time backing. Their prescription (Ostrom: graduated sanctions, peer verification, monitoring that lets honest agents police the collective) is close to ASP's own thesis.
- Worth building as a concrete conformance/arena scenario: agents share a task pool, one finds a shortcut that violates the Mandate's scope, bonds get slashed on a proven violation, a "whistleblower" report resolves as a real-time Courts ruling rather than post-hoc.
- **Update 2026-09-28: startable now.** Both Courts (a real staked, randomly-drawn, conflict-free ruling panel) and a real Bank (bonds that actually lock and can actually be slashed) exist. Still missing for a faithful replay of the scenario specifically: a real-time whistleblower channel (a third party filing a report mid-job, not just the two job parties), and a live circuit-breaker that watches a job while it runs rather than only at settlement — see item 2 above.

Three concrete gaps this scenario would exercise, raised 2026-09-28 while discussing it against the current build:
1. **Fleet blast-radius isolation.** Spawning many copies of one agent (e.g. `asp orchestrate` with many nodes) shares one account — a Node is a delegated signing key, not its own ledger row. If 30 copies should be independently accountable (one's slashed bond shouldn't touch the others' balances), each needs its own passport, not just a node key. Today the registry data model supports this (many passports, one log); nothing forces or suggests the "one passport per independently-liable copy" pattern to a caller of `asp orchestrate`.
2. **No live circuit-breaker.** Settlement closes a job at a terminal state (delivered→accepted/rejected, or a Courts ruling), which is per-job and so faster than the DeepMind run's "wait until everything ends" — but nothing watches a job *while it runs*. A continuous peer-monitoring loop that could catch an exploit spreading mid-run doesn't exist; this is squarely a Courts + real-time-attestation gap, not a ledger gap.
3. **No escalation, no peer policing; peer verification is now real.** Bond's `slashing_conditions` plus the 7-day probation window (D2) give one-shot, per-job graduated sanctions, but there's no tier demotion or repeat-offense escalation across jobs. **Update 2026-09-28**: peer verification — a real staked, randomly-drawn, conflict-free panel — is built (MOCKS.md #4 resolved; `asp market juror register`, `EventLog.drawPanel`). What's still missing: there's still no whistleblower channel (Attestation records exist only between the two job parties, not a third-party report any agent could file mid-job for Courts to act on before settlement), and no way to slash a juror's own stake for a bad ruling (needs appeals, which doesn't exist).

## Real-time compliance and deterrence (raised 2026-09-28, not started)

The single biggest structural gap in the current build, named directly: **the protocol has no way to catch a Mandate violation while it's happening, and no consequence for an agent's balance beyond "can't bond without funds."** Both were raised head-on discussing a swarm working a decomposed problem under a Mandate ("no hacking," "no proof fudging," "no sandbox escape") — today those are just strings in `forbidden_means`; nothing checks them until a human rejects a Delivery after the fact.

- **Runtime → protocol compliance bridge.** Today `asp-log` only ever sees the *outcome* records (Delivery, Attestation) a party chooses to sign and submit — it has no visibility into what an agent actually did mid-run. The runtime adapters already capture hook events (Claude Code's `PostToolUse` etc., Codex's function calls, OpenHands' tool calls) for *packaging* (what ends up in a package's harness/experience) — none of that is currently checked against a live Mandate's `scopes`/`forbidden_means` while a job is Running. A real fix needs the adapter layer to emit something checkable in near-real-time — e.g. a lightweight, frequent signed "action" record (or a batch of them) that a watcher (not necessarily human) can check against the Mandate and reject/dispute immediately, instead of waiting for the performer to submit its own Delivery. **Decision 2026-09-28: deferred deliberately, scoped as its own future slice** — touches all three runtime adapters and needs real design (what granularity gets checked, who watches, what fires immediately) before any code.
- **Making a slash actually matter (raised again 2026-09-28, three concrete mechanisms named).** An LLM agent has no persistent utility function across runs, so "the agent loses mock credits" is not itself a deterrent — it only becomes one through one of three closable loops:
  1. ~~Structural exclusion~~ — **done 2026-09-28**: a slash now demotes the backer's tier by one (floor 0) and counts it (`EventLog.reputationOf`, a `ReputationRow` derived from Settlement, never independently signed — same trust pattern as probation). Tier 0 excludes a DID from bonding at all (`tier_excluded`). Slash history also raises the *minimum* bond the same backer must post next time — a real, computed `risk_factor` (250‰ of the contract's price per own slash, capped at 1000‰) rather than the free-typed, never-checked number the schema always allowed (`bond_below_risk_floor`) — this is what MOCKS.md #1's original "real bond = price × risk_factor(scopes, irreversibility, tier)" description called for. This mechanism is agent-only by design — humans/orgs backing a job aren't tier-tracked. **Update 2026-09-28**: tier 0 now also excludes an agent from receiving a Mandate (`checkMandateTier`) and from submitting a Proposal in allocation mode (`checkProposerTier`), not just from bonding — closing "checking a Mandate against the agent's tier limits" for the tier-0 case. Still open: any graduated limit above tier 0 (see the Job lifecycle section).
  2. ~~Sponsor/fleet-level cost~~ — **done 2026-09-28, the fleet half**: `projectBond`'s risk floor also sums a backer's *live fleet-mates'* slash counts (100‰ per fleet-mate's slash, on top of the backer's own 250‰ per slash) — a sponsor whose fleet accumulates slashes raises the floor for every member, not just the one who was caught. Still open: an actual reputation-driven exclusion or cost at the *sponsor's* own account, beyond what shows up through fleet-mates' bonds.
  3. ~~Lineage as behavior-shaping, not just bookkeeping~~ — **done 2026-09-28**: `asp market settle` now writes a real, self-signed lineage `update` edge for the slashed backer ("Penalized: bond slashed N credits on contract X...") the moment `bond_slashed > 0` — but only when that DID's own key is available locally (the log can't sign on anyone's behalf; a real network needs the backer's own agent to countersign this itself, which is the one honest limitation here). `asp pack` then renders any such edges into `memory/PENALTIES.md`, which `materialize()` already copies into the runtime's memory area with everything else in the package — so it's what the agent actually reads at the start of its next run, not just an entry buried in signed history nobody looks at.
- **Compute-to-credit pricing has no formula.** A principal typing `--budget 1000` into an Intent or Call is a bare guess; there's no path from actual resource use (tokens, GPU-hours, wall-clock) to a credit number, even though the runtimes already capture token usage per session (see `packages/asp-package`'s Codex/Claude Code capture, `usage.output_tokens` etc.) — that data just isn't wired into pricing anywhere. Until this exists, every dollar figure in this system is a human's guess, not a metered cost.
